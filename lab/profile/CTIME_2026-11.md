# Compile time by phase, November 2026

Measured 2026-11-04 on a GitHub Actions runner (4 cores, Ubuntu 24.04, Python 3.12.3, gcc 13.3.0), base
`staging:integ` / `origin/integ`, from `lab/profile/run.py --runs 3`.  Each cold build gets a fresh
`AIL_CACHE` and `TMPDIR`, runs under `ulimit -v 1500000`, with `AIL_SERVER=0` and `AIL_NO_CACHE=1`
(so the old whole-build `cc` cache cannot hide the gcc time).  All times are seconds, median of 3.
The compiler child is allowed to write `__pycache__`, as `_compiler_python()` does in a real build;
without that, every child recompiles the 180k-line compiler (see "Harness bugs" below).

The parent phase is `wall - child wall`; `_load_sources` is timed directly around the function in the
parent process, so it is a real subset of the parent and is not inflated by cProfile overhead.
`child import` is a fresh `python3 -c "import pyc"` with bytecode warm.  The child is then split into
the part before the C text (key hash + lowering) and C emission.  gcc is split into reading the text
(`-fsyntax-only`) and code generation (`full compile - read`), and the link is reported alone.

## Cold build: share and Amdahl bound

For each task, `share = seconds / wall` and the bound is `1 / (1 - share)`, i.e. the most the whole
build could shrink if that one phase became free.  `_load_sources` is bounded on its own, leaving
the rest of the parent.  gcc read is a subset of the gcc codegen phase, so those two overlap.

## The front-end cache hit

Each pair is a cold build and then a second build with the same `AIL_FE_CACHE_DIR`; the harness now
asserts that the second `AIL_FE_CACHE_LOG` line starts with `hit`.  The `cc` cache stays off, so the
hit still pays the whole gcc compile: this is the front-end cache alone.

`hit child Python` is the child process minus its gcc compile and link; it falls from several
seconds of lowering to the import + key + entry-read cost.  For chain_relax the hit is **0.862 s**
against **2.182 s** cold, below the 1.5 s target.  Tasks whose generated C takes more than about
1.5 s in gcc (berth_sim, tally_lang, term_rank, ticket_audit, tree_fold) stay above 1.5 s with the
`cc` cache off; their bound is gcc, not the front end (see "Next cuts").

## Harness bugs that produced the old numbers

The raw `CTIME_2026-11.json` from `job-ctimeprof-11032049` logged `miss` on every "hit" run: the old
loop built the cold and warm runs in different work directories, so `env_for()` gave each its own
`AIL_FE_CACHE_DIR` and the warm build never saw the cold entry.  It also set
`PYTHONDONTWRITEBYTECODE=1`, which makes `_compiler_python()` pass `-B` to the child: pyc/pyfunc
then recompile from source on every build (about 1.0 s without bytecode against 0.08-0.27 s with
it here).  Sharing the directory and dropping that switch is what turns a "2% faster" hit into the
numbers above; the assertion now fails the run instead of silently recording a miss.  The first
pass also estimated `_load_sources` from a profiled parent scaled by the profiled wall, which
inflated it; the harness now wraps `_load_sources` with a timer in the real parent build.

## Where a cache hit spends its time

Profile of the `pyc.py` child on a chain_relax hit (`cProfile -s cumtime`; cumulative seconds).
The profile adds overhead, so read the shape, not the absolute total: the un-profiled hit built in
0.862 s with 0.140 s of child Python (child wall minus gcc and link).

| function | cumtime |
|---|---:|
| `pyc.py:<module>` | 0.721 |
| `pyc.py:main` | 0.618 |
| `pyc.py:build_cached` | 0.616 |
| `pyc.py:_fe_compile` | 0.583 |
| `pyc.py:_cc` | 0.583 |
| `buildcache.py:run_cc` | 0.583 |
| `pyc.py:<lambda>` | 0.583 |
| `native_diagnostics.py:run` | 0.583 |
| `subprocess.py:run` | 0.583 |
| `subprocess.py:communicate` | 0.583 |

Eight of the ten rows are the gcc subprocess chain (`_fe_compile` -> `_cc` ->
`buildcache.run_cc` -> `subprocess.run` -> `communicate` -> `select`), i.e. compiling the stored C.
The Python work before the lookup is import plus key: the `pyc` module import is about 0.08-0.10 s
here, and `_fe_key`/`sources_hash` about 0.03 s; `fecache.get()` reads and SHA-verifies the entry in
under a millisecond.  The parent has already spent the measured `_load_sources` time before the
child starts.

Import breakdown for the child (`python3 -X importtime -c "import pyc"`, cumulative ms):
`pyc` 79.2, `pyfunc` 49.4, `cruntime` 16.3, `argparse` 5.0, `pipeline` 4.2, `ast` 3.8, `hashlib` 2.1.

A hit therefore costs: parent `_load_sources` (0.071 s) + other parent work (0.103 s) + child import
(0.097 s) + key/entry (0.043 s) + the full gcc compile (0.529 s) + link (0.019 s).  Only the lowering
(cold chain_relax: about 1.367 s) is skipped.  The 3.99 s "hit" in the brief was the old harness:
every run was a miss, and no-bytecode imports added about a second; with a shared directory and
normal bytecode the chain_relax hit is 0.862 s.
