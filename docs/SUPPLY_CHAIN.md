# Supply chain: what an AIL binary contains and links

An AIL build turns Python syntax into C and asks the host C compiler to link that C. The
result is a normal ELF executable, but its inputs come from four places: the AIL compiler
itself, the AIL runtime and standard library, the C toolchain and system libraries, and
optional Rust crates. `tools/sbom.py` records those inputs as a CycloneDX 1.5 JSON document.

Measurements for the current corpus are in [`lab/sbom/RESULTS.md`](../lab/sbom/RESULTS.md).

## What AIL ships

| part | where it lives | how it reaches a binary |
| --- | --- | --- |
| compiler | `AIL_CURRENT/ail_chatgpt.py`, `AIL_CURRENT/*.py`, `AIL_CURRENT/python/pkg-v12/` | generates `program.c` or `entry.c`; the compiler is not inside the executable |
| AIL standard library | `AIL_CURRENT/stdlib/*.py` | source is lowered into the generated C |
| runtime headers | `AIL_CURRENT/python/pkg-v12/*_core.h` (`ailfile_core.h`, `ailproc_core.h`, `ailpath_core.h`, `ailsql_core.h`, `ailhttp_core.h`, `ailurl_core.h`, `ailhash_core.h`) | the header text is embedded in the generated C when the program uses that layer |
| bundled C | `AIL_CURRENT/stdlib/zlib_glue.c` with `zlib_glue.h` | compiled into the FFI adapter object and linked into the executable |
| FFI adapters | generated by `ail_ffi_lower.py` | one generated `ffi_adapter.c` object per build that declares `@extern` stubs |

A program that does not use one of these layers does not carry it. For example, a program
that uses only integers, strings and lists embeds no runtime core header and links only libc;
`import zlib` embeds `zlib_glue.c` and links `libz`.

## What a binary links

`readelf -d BINARY` is the authoritative list of shared libraries in the executable
(`DT_NEEDED`). On a typical Linux build the list is `libc.so.6` plus any library named by an
`@extern(lib=...)`, such as `libz.so.1`, `libm.so.6` or `libsqlite3.so.0`. The link line is
recorded by the compiler in `DIR/native_report.json` when `--debug-dir DIR` is passed, so the
SBOM can show both sides: the flags the compiler asked for and the libraries that survived
linking (`--as-needed` may drop an unused `-l` flag).

A Rust crate example also links a static archive (`./libfnvhash.a`). That archive leaves no
`DT_NEEDED` entry, so the crates are read from the nearest `Cargo.lock` instead. A crate that
a build does not use is still listed if it is in that lock file; the Cargo.lock is the
dependency set Cargo resolved for the crate directory.

## Get an SBOM

Build the program with a debug directory, then run the tool:

```sh
python3 -B AIL_CURRENT/ail_chatgpt.py compile examples/ffi/zlib_check.py \
    -o /tmp/zlib_check --debug-dir /tmp/zlib_check.d

python3 tools/sbom.py /tmp/zlib_check \
    --source examples/ffi/zlib_check.py \
    --debug-dir /tmp/zlib_check.d \
    -o /tmp/zlib_check.cdx.json
```

The document contains:

* `metadata.tools`: the AIL compiler (`ailc`) version and the C compiler with its version;
* `metadata.properties`: the AIL git commit, the source path, the recorded link line and the
  compiler banner;
* one `library` component per `DT_NEEDED` library, with its `soname`, resolved path, Debian
  package name and version where `dpkg -S` / `dpkg-query` can tell them, and its licence where
  the package copyright names one;
* one `file` component per bundled C source or runtime header, with its sha256;
* one `library` component per crate in the nearest `Cargo.lock`, with its version, purl,
  checksum when Cargo recorded one, and licence when the crate manifest names one;
* a `dependencies` entry from the executable to every component.

Add `--check` to write the document and print a cross-check:

```sh
python3 tools/sbom.py BINARY --source SRC --debug-dir DIR -o out.cdx.json --check
```

It compares the BOM with `readelf -d`, the link line in `native_report.json`, the bundled
sources visible in the generated C and the nearest `Cargo.lock`. The command exits 0 only
when every `missing` and `extra` list is empty. `validate_bom()` performs the built-in
CycloneDX 1.5 check (required fields and references); it does not download a schema.

## Check a build is reproducible

Reproducibility is a separate measurement: build the same source twice with different build
directories, `TMPDIR`, `HOME`, `PYTHONHASHSEED` and `SOURCE_DATE_EPOCH`, then compare the
executable and the generated C by sha256:

```sh
python3 tools/repro_check.py -j 2 --filter examples/
```

The tool and its whole-corpus results are in [`tools/repro_check.py`](../tools/repro_check.py)
and [`lab/repro/RESULTS.md`](../lab/repro/RESULTS.md). Today most programs are byte-identical;
the recorded exceptions are absolute source paths embedded in `__file__` and in FFI symbol
tags. An SBOM describes what went into one build; `repro_check.py` describes whether another
build of the same source produces the same bytes. Neither replaces the other.

## Not covered yet

* There is no `--sbom` flag in `ail_chatgpt.py` or `packaging/ail_lang/cli.py` yet. The
  follow-up hook should run the same code as `tools/sbom.py` after a successful build and
  place the document beside the executable. Until then the two commands above are manual.
* Transitive shared-library dependencies are not expanded. The BOM lists the libraries the
  executable names in `DT_NEEDED`, not everything those libraries load in turn.
* Libraries opened at runtime with `dlopen` (and plugins) are invisible to `readelf -d` and
  are not listed.
* System header files and the C compiler's internal headers are not components; only the C
  compiler version and the bundled AIL headers are recorded.
* Crate licences are only filled in when the crate manifest has a `license` field; registry
  packages are not queried over the network.
* The BOM has no vulnerability data, signatures or attestations.
* The crate corpus cannot be built on a runner without a Rust toolchain; `tools/sbom.py`
  still reads each `Cargo.lock`, but the executable-side cross-check for crates requires the
  corresponding binary.
