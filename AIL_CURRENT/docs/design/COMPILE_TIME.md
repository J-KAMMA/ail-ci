# Compile time: a priced plan (design only, 2026-10-30)

Plan for cutting the time `ail compile` takes, roadmap item 3. Nothing here changes the compiler. Every cut is priced from
measured shares before anyone builds it (the `speed-claims` rule), judged on binary size and memory as well as speed, and
adopted only with proof that program output did not change (the `optimization-adoption` rule).

Fixed constraints (owner decisions): gcc stays at `-O2`; `-march=x86-64-v3` is opt-in only; LTO is rejected. Program
output (stdout, exit code) must be identical before and after every change.

Status words used below: **[measured]** = a number from a run named in section 1; **[measured here]** = one of the few
compiles run while writing this note (section 1.4, laptop, noisy); **[estimate]** = derived from measured shares, not
measured itself; **[unmeasured]** = no number exists yet.

## 1. Baseline

### 1.1 Where a build's time goes (GitHub runner)

Source: the `profile-lab` workflow (`lab/profile/run.py`, `.github/workflows/profile-lab.yml`, PR #196). It is on `main`
and `ci-speed`, **not on `integ`**. Method: wall = median of 3 runs of `ail_chatgpt.py compile --no-cache`; gcc time =
a `$PIPE_CC` wrapper around every C compiler call; the Python remainder is split by one cProfile run (own time by module,
waiting on children excluded), with a heuristic module-to-phase map. 19 programs profiled (bench, examples, corpus
Python), 8 skipped because they are refused.

| phase | run 40811435899 (ci-speed 58232db5, 2026-10-29) | run 40727170998 (main, 2026-10-28) |
|---|---|---|
| C compiler (gcc, all calls) | 15.0 s, **59.2%** | 22.9 s, 57.2% |
| startup: imports and module bodies | 0.9 s, 3.4% | 1.4 s, 3.5% |
| driver (ail_chatgpt, syntax, modules) | 0.1 s, 0.2% | 0.1 s, 0.2% |
| front end (analysis, types) | 0.2 s, 0.9% | 0.4 s, 1.0% |
| IR and lowering | 0.1 s, 0.4% | 0.2 s, 0.4% |
| C generation (emitters, runtime text) | 4.3 s, **17.0%** | 7.2 s, 18.0% |
| stdlib and other Python | 4.8 s, **18.8%** | 7.9 s, 19.8% |
| total wall | 25.3 s | 40.1 s |

The "59% / 18% / 19%" quoted in the task files (`tasks/ctime1.md`, `ctime2.md`) mixes the two runs: gcc 59.2% is from
10-29, C generation 18.0% from 10-28. The 10-28 runner was about 1.6x slower overall, but the shares agree within 2
points. **[measured]**

Per program (10-29 run): wall 0.47-3.29 s; gcc share median 60%, min 43% (`bench/csv_table`, the Python-heaviest),
max 75% (`t172`). Median compile time over the 194 corpus programs that pass, from the same run's real-program check:
**2.03 s** (run 2 at a time beside timed runs, so a little high). Median binary 75 KB. **[measured]**

Caveats: the Python split is a cProfile run, which inflates pure-Python time (the listed function table sums to about
18.1 s of profiled time against 10.3 s of measured Python wall), and the module-to-phase map is a heuristic. The gcc
share is not affected: it is timed by the wrapper.

### 1.2 Inside gcc: runtime prelude vs the program's own code (runner)

Source: job ctime2 (`lab/profile/GCC_SHARE.md` and `measure_gcc_share.py` on branch `job-ctime2-10290148`, commit
776f34b5, not merged). 20 corpus programs, `gcc -c` with the build's own flags, median of 5, gcc start-up floor
(8.2 ms) subtracted. The prelude is the generated text before the program's own section; it compiles on its own as a
translation unit.

| measure | value |
|---|---|
| gcc `-c` time, 20 programs | 26,743 ms |
| of which prelude alone | 4,987 ms, **18.8% pooled** (mean 19.5%, median 17.9%, range 2.0-58.9%) |
| general path / typed path | 20.3% / 13.1% pooled |
| prelude bytes / generated bytes | **93.0%** |
| smallest program (`print(0)`, typed) | about 11 ms of gcc per build for the fixed base |

General-path programs dominate gcc time: their C is 557-684 KB and costs 1.1-2.8 s of gcc on the runner; typed-path C
is 161-554 KB and mostly 0.3-0.6 s. **[measured]**

Reading this correctly matters for the plan. "Prelude alone" compiles with every *unused* `static` function dropped
before optimisation, so 18.8% is the cost of the text itself. The other 81% is **not** the program's own source: in the
full unit, the runtime functions the program reaches are optimised again on every build. Section 1.4 shows the
program-specific text is about 1% of the bytes.

  The tail of slow builds is Python (mixed-mode `pymix` trying candidates), not gcc. **[measured]**
- Job ctime3 (2026-10-23, merged as 3600e0d0): confirmed the content-addressed cache already exists

### 1.4 New measurements for this note (laptop)

Machine: the WSL laptop (16 threads, 6 GB), gcc 13.3.0, tree `integ` d68453f7, load average 4-7 from other agents.
Wall time here swings up to 3x, so only user time and ratios within one file are used; nothing below is a speed claim.

```sh
cd AIL_CURRENT && python3 -m compileall -q -j 2 .
python3 ail_chatgpt.py compile --no-cache --syntax python --debug-dir $O/t078 -o $O/t078.bin \
    ../lab/corpus/programs/deepseek-v4.1-flash-free/t078.py          # and glm-5.3-flash-free/t010
F="-fno-tree-slp-vectorize -ffp-contract=off -fopenmp-simd -fno-asynchronous-unwind-tables"
gcc -fsyntax-only $F t078.c ; gcc -O0 $F -c t078.c ; gcc -O1 $F -c t078.c
gcc -O2 $F -ftime-report -c t078.c
head -c <offset of "interned attribute-name ids"> t078.c > pre.c
gcc -O2 $F -w -c pre.c ; gcc -O2 $F -w -fkeep-static-functions -c pre.c
```

| t078 (general path) | user s | `.text` of the object |
|---|---|---|
| whole build (`compile`, Python + gcc + link) | 5.25 + 0.67 sys | binary 86,816 B |
| `-fsyntax-only` (parse only) | 0.21 | - |
| `-O0 -c` | 1.04 | 164,392 B |
| `-O1 -c` | 2.50 | 79,100 B |
| `-O2 -c` (the build's level) | 4.83 | 74,368 B |
| prelude alone, `-O2`, unused statics dropped | 1.61 (**33%** of full; the runner measured 33.8%) | 22,894 B |
| prelude alone, `-O2 -fkeep-static-functions` | 3.31 | 54,094 B |

- Generated C: 668,133 B, of which **7,117 B (1.1%)** is the program's own section; t010: 634,302 B, 8,283 B (1.3%).
- `-ftime-report` at `-O2`: "phase opt and generate" 72% (t078) / 74% (t010) of gcc wall, "phase parsing" 28% / 26%;
  "callgraph functions expansion" (per-function optimisation and code generation) alone 59% / 61%.
- gcc peak RSS: 88-94 MB at `-O2`, 68-70 MB at `-O0`, 34 MB for `-fsyntax-only`. The whole `compile` peaked at 88 MB
  (t078) and 94 MB (t010), so gcc, not Python, sets the build's memory.

Observations that are not cuts but belong to the owner:

- **t010 changed path.** On 10-28 (ctime2) it built on the typed path (160,866 B of C, 324 ms of gcc on the runner). On
  `integ` d68453f7 it builds on the general path ("main() needs the tagged-int lowering ... GeneratorExp"), 634,302 B of
  C. A typed-to-general move quadruples the C and is the single largest compile-time swing seen. Unverified whether this
  is a regression or a deliberate refusal.
- **The general prelude grew.** t078's C was 587,547 B on 10-28 and 668,133 B on 10-29 (+13.7%); the program section
  did not change size much. The trees differ (ctime2 exported `staging:integ`), so this is indicative only. Nothing in CI
  tracks generated-C bytes.
- **The general prelude relies on `-O2` to link.** gcc warns `'ail__floordiv_slow' used but never defined` (and about
  15 more `static` big-int helpers) and about their implicit declarations. At `-O2` the calls are folded away. Any cut that
  compiles the runtime separately or at another level must define or drop them first. Link at `-O0` was not tried.

## 2. Candidate cuts

Prices are shares of build wall on the runner baseline (gcc G = 59.2%, Python P = 40.8%). "Upper" is the Amdahl bound
if the attacked part went to zero or to its measured floor; "realistic" says how it was derived. Bounds for reference:
removing all gcc gives 2.45x, removing all Python 1.69x.

### 2.1 Finish what is built: PR #207 and job ctime1 (Python)

- **PR #207, unprintable table.** Attacks 15.8% of profiled Python = about 6.4% of a build. Upper **6.4%**; realistic
  **4-6%** (the PR's own -18% / -24% CPU on two probes is on repr-heavy programs, so it is the high end). Binary:
  byte-identical (the PR's check). Run time and memory: unchanged by construction; the on-disk table adds one small file
  under `$AIL_CACHE`. Proof: byte-identical executables, typed and general builds, which the PR already shows.
- **ctime1, walk reuse.** Reviewer's ratio 34.64 -> 20.54 s on the Python side. If that ratio held on the profile set:
  `P x (1 - 20.54/34.64)` = **16.6%** of a build, upper. Realistic **8-12%** **[estimate]**: one sample of 20 programs,
  timed on the laptop, and it overlaps with neither #207 nor gcc, but laptop ratios have been optimistic before. Binary:
  generated C byte-identical on 219/219 corpus programs (reviewer), so binaries and run time are unchanged. Remaining
  work is records only: regenerate `MANIFEST.json`, a DEVLOG entry, a commit message with the share and the numbers.
- CI-only: byte-compiling the compiler (part 2 of #207) removes 1.3-1.6 s per compile on a cold runner. It does not
  touch users (an installed package has its bytecode).

### 2.2 Runtime split: compile the runtime once, cache it, compile only the program per build (gcc)

The largest lever. A build would compile only the program's section plus the declarations it needs, and link a runtime
object or archive built once per (runtime text hash, compiler identity, flags) and stored in the existing build cache.

- Price. Today the full unit costs 4.83 s user for t078 while the program's own text is 1.1% of it, parse alone is
  0.21 s, and the *whole* runtime at `-O2` costs 3.31 s once. Per-build work after the split would be the declaration
  parse, the program's functions, the `static inline` helpers it must still see, and a link. Upper: gcc down to about
  0.3 s of 4.83 = **about 90% of gcc = 53% of a build (2.1x)** **[estimate from measured parts]**. Realistic:
  **50-70% of gcc = 30-41% of a build** **[estimate; the split was not built]**, because the hot helpers must stay
  inline in the header (next point) and the link grows.
- Run-time speed: **the main risk.** Today every runtime function is `static` in the same unit, so gcc inlines and
  IPA-clones runtime code into the program at `-O2`. A separate object loses that, and LTO, the usual repair, is
  rejected. Mitigation: keep the hot small helpers `static inline` in the header and move only large or cold functions
  (`AIL_BIGFN` / `AIL_BIGCOLD` are already `cold, noinline`) into the object. How much of the runtime can move without
  an instruction-count loss is **[unmeasured]** and is the question step 2 answers.
- Binary size: an archive linked with `--gc-sections` keeps only used members, but loses dead-argument elimination and
  constant propagation across the boundary; it may grow or shrink **[unmeasured]**. Peak memory of the build should
  drop (gcc on a small unit; 88-94 MB now). Disk: one cached object per distinct runtime text; how many distinct texts
  the corpus produces (the typed path selects pieces per program) is **[unmeasured]**; if many, cache per piece.
- Also fixes a cache gap: the `cc` key is the whole C text, so editing one line of a program misses the whole compile.
  After the split, the runtime object hits across edits and across programs.
- Prerequisite: the undefined `static` big-int helpers (section 1.4) must be defined or removed.
- Proof the output is unchanged: binaries will differ, so byte identity is not available. Use (a) the program section of
  the generated C byte-identical before/after apart from the declared `static`-to-`extern` edits (`tools/codegen_diff.py`),
  (b) stdout and exit code identical to the pre-change build and to CPython on all 219 `lab/corpus/programs` and the
  bench programs, (c) instruction counts (`tools/icount.c`) on the bench programs, (d) the full `par_check` once after
  merging.

### 2.3 Emit less C: drop runtime pieces nothing reaches (Python and gcc)

gcc already drops unused `static` functions before optimising, so this saves their parse in gcc plus the Python time
that builds their text. Upper: the prelude-alone cost, **18.8% of gcc = 11% of a build**, plus part of "C generation"
(17% of a build; the runtime-text share of that phase is **[unmeasured]**). Realistic: about the parse share of the
prelude, 4-6% of gcc **[measured here: -fsyntax-only 0.21-0.25 s of 4.8-5.8 s]**, plus a Python saving **[unmeasured]**
= **3-6% of a build** **[estimate]**. Binary: if only functions gcc would drop anyway are removed, the executable is
**byte-identical**, which is the proof (`cmp` on every corpus and bench binary). Run time and memory: unchanged. Cheap
to verify, small win; it also keeps the C size growth (section 1.4) in check.

### 2.4 Precompiled header for the runtime (gcc)

gcc PCH removes parse only, and needs the header first in the unit, the same flags and the same gcc version. Upper:
"phase parsing" 26-28% of gcc wall at `-O2` = **16% of a build**; realistic: closer to the `-fsyntax-only` share, 4-6%
of gcc = **about 3% of a build** **[estimate]**. Disk: a PCH of a 650 KB header is tens of MB **[unmeasured]**; one
per distinct runtime text. Proof: executables should be byte-identical; `cmp` them. Worth it only if 2.2 is refused,
and it overlaps 2.3 (both attack parse).

### 2.5 `-O2` on hot code, `-O1` on cold runtime parts (gcc)

Measured on t078's whole unit: `-O1` costs 2.50 s against 4.83 s at `-O2` (52%), `.text` 79,100 B against 74,368 B.
Which part of gcc's time is cold runtime code is **[unmeasured]**; `AIL_BIGFN` functions are already `cold`, which gcc
optimises for size. Upper if half of the optimisation time were cold code: about a quarter of gcc = 15% of a build;
realistic **[unmeasured]**, likely small. Run time: any changed code needs `icount` on the bench; binary size grows a
little. It contradicts the owner's "keep `-O2`" decision in spirit (per-function `optimize` attributes are also
documented by gcc as not for production use). **Not recommended** unless the owner reopens the flags decision.

### 2.6 Parallel gcc per translation unit (gcc)

A normal build is one unit (typed or general). Mixed-mode builds compile the typed clones and the boxed unit one after
another, then link (`pyc.py`, the `mix_units` loop). Running those in parallel saves `(n-1)/n` of the clone compiles,
but only for mixed builds, whose share of builds is **[unmeasured]** (the code comment says the overwhelming majority
take the single-unit path). Splitting a single unit to parallelise it loses inlining, the same risk as 2.2 without the
caching benefit. On this laptop, where several agents compile at once, parallel gcc would also raise peak memory.
Realistic: **about 0% for the median build**. Not recommended now.

### 2.7 Content-hash cache (exists)

`buildcache.py` already caches both the gcc call and the whole compile by content. Remaining gaps: (a) the `cc` key
covers the whole unit (2.2 fixes it); (b) the `fe` key includes every compiler source file's bytes, so each compiler
commit invalidates all entries, which matters for CI and development only. No new cache is proposed. CI and the
profile run with `--no-cache` on purpose, so cache wins never show in these numbers.

### 2.8 Profile the rest of the Python side

After 2.1 lands, what remains of P is unknown. The 10-29 profile points at `isinstance` (20.7%), the AST iterators
(8.4%) and `pyfunc._etype` (5.1%), which are spread over many callers. Price each again from a fresh profile-lab run
before building. The slow tail (`g01_008`, 30 s, mixed-mode candidates) is a separate, Python-only target: ctime
measured `pymix`'s per-candidate `pyfunc.to_c` at 36% of that program; cutting it needs a decision change, so it is out of
scope here.

## 3. Recommended order

1. **First step, cheap and measurable: land the two built Python cuts and re-baseline.** Review and merge PR #207; fix
   ctime1's records (manifest, DEVLOG, commit message with share and numbers) and merge it. Both already have
   output-identity proofs. Then run `profile-lab` once on the result. Cost: two reviews and one CI run, no new code.
   Expected: build wall down **10-17%** combined **[estimate]**; the run gives the new P and G to price everything after.
2. **Measure the runtime split before building it.** A lab script only (`lab/profile/`), no compiler change: for the 20
   ctime2 programs and the bench programs, take `--debug-dir` C, move the runtime's non-inline functions into one object
   compiled once, compile the program section against declarations, link, and record gcc time, link time, binary size,
   peak RSS, `icount` of each bench program, stdout/exit identity, and the number of distinct runtime texts. Gate to
   build it for real: realistic gcc saving at least 40% **and** no `icount` loss beyond run-to-run noise on any bench
   program. If the gate fails with all helpers inline, try moving only `cold` functions; if that also fails, drop 2.2.
3. **Emit less C** (2.3), whichever way step 2 goes: small, and its proof is byte-identical binaries. Add a CI number for
   generated-C bytes per program at the same time so growth like section 1.4's is visible.
4. **PCH** (2.4) only if 2.2 is refused.
5. Re-profile Python (2.8) after each merge; price the next hot function from that run.
6. Do not do 2.5 or 2.6 now.

## 4. Benchmark protocol

- **Machines.** Shares and wall time: a GitHub Actions `ubuntu-24.04` runner through `profile-lab` (CPython 3.12, gcc
  13.3, nothing else on the VM; shard 0 profiles before anything else runs). Run-time speed: the laptop, instruction
  counts only (`tools/icount.c`, deterministic where wall time swings 3x). Laptop wall times are never a speed claim.
- **Programs.** (a) The 19 programs `profile-lab` profiles (bench, examples, corpus Python); (b) the 20-program ctime2
  sample (seed 20261028), which splits prelude from program; (c) all 219 `lab/corpus/programs` for output identity;
  (d) the slow gdev tail (`g01_008` and the 5 slowest of ctime's 40) for the Python-side tail; (e) the `bench/` programs
  for `icount`.
- **Compile measurements.** `ail_chatgpt.py compile --no-cache`, warm `__pycache__`, median of 3 per program; gcc time
  from the `$PIPE_CC` wrapper; Python CPU as user+sys; report total, median and the 5 slowest; peak RSS of the build
  (`/usr/bin/time -f %M`); generated-C bytes; binary bytes. Report the cache-hit path once per change (a warm `fe` hit
  should stay about 0.1 s).
- **Run-time measurements.** `icount` per bench program, base and change interleaved; any increase beyond the
  run-to-run spread fails the change. Peak RSS of the program.
- **Identity.** For changes that keep binaries: `cmp` every executable. For changes that do not (2.2, 2.5): stdout and
  exit code on all 219 corpus programs against the base build and CPython, `tools/codegen_diff.py` on the program
  section, and the full suite through `tools/par_check.py` once after the merge (not per job).
- **CI job.** `profile-lab` (weekly, manual, and on push to its own paths). It is not on `integ`; bringing
  `lab/profile/` and the workflow onto `integ`, plus ctime2's `measure_gcc_share.py`, makes the baseline track the branch
  the work merges into.

## 5. Risks and open questions

Risks:

- **Run-time speed of 2.2.** The single-unit build is what gives gcc its cross-function view. With LTO rejected, only the
  header/object split can be tuned; step 2 measures it before anything is built.
- **Laptop prices are optimistic.** ctime1's 1.69x is a laptop ratio from one reviewer run. Earlier pricing on this
  laptop missed by 1.6-3x; step 1's runner re-baseline is the check.
- **Cache-key correctness** for a shared runtime object: compiler identity, flags, target (`--target`, `--static`,
  `--freestanding`, `--m32`) and the runtime text must all be in the key; a wrong hit would silently link an old runtime.
  `buildcache.py`'s rules (a hit is byte-for-byte what a miss makes; anything odd is a miss) must cover it.
- **Cross-targets** (zig cc for Windows/macOS/arm64) need their own runtime objects; first builds per target stay slow.
- **The general prelude's undefined `static` helpers** (section 1.4) are a latent build hazard at any level but `-O2`.

Open questions for the owner:

1. Is a separately compiled runtime acceptable under the flags decision (still `-O2`, no LTO) if `icount` shows no
   loss? What loss, if any, is tolerable for what compile-time gain?
2. Is it acceptable that executables change bytes when stdout, exit code and `icount` are unchanged (2.2, 2.5)? The
   other cuts keep binaries byte-identical.
3. Rule out per-function `-O1` (2.5) under the flags decision? This plan recommends ruling it out.
4. What is the target: a median compile time (now 2.03 s on the runner), or a place in the language comparison table
   next to C, Rust, Go and Nim? Compile time is not yet a comparison column.
5. Should `profile-lab` and `lab/profile/` move onto `integ`, and should generated-C bytes per program become a CI number?
6. t010 moved from the typed to the general path between 10-28 and 10-29 (4x the C). Regression or intended?
7. Merge PR #207 and ctime1 as step 1?
