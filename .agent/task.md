Lane: fuzzpy

**Correctness: differential fuzzing of plain-Python sources on the typed path. Find and file; do not fix the compiler.**

1. Write `lab/fuzzpy/gen.py`, a seeded generator of small, valid Python programs that use what the typed path claims to support:
   - ints near the int64 edges;
   - lists, dicts, str and bytes;
   - slices, comprehensions;
   - small classes, recursion, exceptions.

   Every program prints its results.
2. Run 2,000 programs through `ail run` (default build) and CPython, comparing stdout, stderr's last line and exit status. Use `ulimit -v 1500000` and a 10-second timeout each.
   - Count only differences that are not explained by an owner decision. int64 overflow stops loudly by design; a loud stop where CPython keeps going is correct. Classify those separately.
3. For each distinct cause, reduce it to a minimal program and add it under `lab/fuzzpy/findings/NNN.py`, with the expected CPython output and a one-line cause guess.
4. Write the summary in `lab/fuzzpy/REPORT.md`: programs run, typed-path share, the differences per class, and silent wrong outputs listed first.

Do not edit compiler sources. Time budget: 80 minutes.

**Rules for every job.**
- **Load:** you are one of up to five agents on a 16 GB PC. Keep local parallelism at 2 (`-j 2`) and never run the whole suite; the full suite runs on CI after merge.
- **Commits:** commit with explicit `git add` on your branch. Messages end with `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`.
- **Forbidden:** push, stash, rebase, reset, and deletion outside /tmp.
- **Records:**
  - New DIFFERENCES rows use placeholder ids `C?-<your branch>-N`.
  - Add a DEVLOG entry at the top with today's date.
  - Register a new test module: if `AIL_CURRENT/tests.d/` exists, add `AIL_CURRENT/tests.d/<module>.txt` containing the module
    name and do NOT edit the tuple in `ail_check.py`; otherwise append it to the `MODULES` tuple.
  - `git add` new files, run `python3 tools/update_manifest.py`, then `--check`. Do not hand-edit `MANIFEST.json` or `manifest.d/`.
- **Required tests:** the targeted modules for what you touch, plus test_ail_safetynet, test_ail_files and test_ail_corpus_findings3. Run them on your final commit, not an earlier one.
- **Mandatory self-check before you report.** A reviewer will repeat it, and past reports were wrong about half the time.
  1. Write probe programs in /tmp/probes/ for every behaviour you changed. Cover the boundaries your implementation implies, not only the example: types, widths, empty, negative, aliasing, values reaching the code through an argument, a list item, an attribute and a dict value, and both builds.
  2. Run each probe with `bash ~/tools/cmp.sh /tmp/probes/<p>.py $PWD`.
  3. Every probe must match CPython or be refused by name.
  4. List the probes and their results in the report.
- **Never claim something works unless a probe or test you ran shows it.** If you did not verify something, say so.
- **Tokens:** use grep -n, narrow reads, and `tail` on long logs.
- **Budget:** stop at the budget note, leaving a committed, consistent state.
- **Report:** keep it brief, with numbers.
- Test data: email addresses only on example.com / example.org (the public export audit rejects any other domain).

**Work in few steps** (each step costs model time):
- Write all probe programs first, then run them together with one command, for example a loop over `bash ~/tools/cmp.sh`, instead of one command per program.
- Search only inside the repository (`grep -rn ... AIL_CURRENT tools`), never across `/home` or `/tmp`.
- Read a file once, using a range that is large enough, instead of many small reads.
- Do not re-run a test that already passed unless you changed code since.
